- 개발 기간: **2026-10-30 13:00 ~ 2026-10-31 12:00, 한국시간(KST)**.
- 팀 구성: **4명**.
- 필수 제출물: **실행 가능한 프로그램 완성본 + 발표자료**.
- 내부 제출 목표: **10월 31일 11:00**. 마지막 1시간은 제출 문제 대응에 사용합니다.
- 권장 GitHub 저장소명: **`honsal-index`**.
- 저장소 설명: 강원도 1인 가구를 위한 생활 편의 점수·동네 비교·맞춤 추천 서비스.

이 문서는 이번 마감의 실행 계획입니다. 기존 개발 계획의 다도시 확장과 고도화는 이번 필수 범위에서 제외합니다. 일정은 총 23시간이며, 수면 4시간·식사 1시간·제출 여유 1시간을 포함합니다.

**한 도시에서 사용자가 동네를 선택하고, 생활 편의 점수와 근거를 확인하고, 두 동네를 비교하며, 가중치에 따라 추천 순위가 바뀌는 웹 프로그램**을 완성합니다.

## 병렬 작업을 위한 약속

13:30까지 다음을 합의하고, 수집 완료 전에는 **테스트용임이 표시된 3행 샘플**을 공유합니다. 이 샘플은 최종 실제 데이터와 섞지 않습니다.

- 공통 식별자: `area_id`는 문자열. 지역명 대신 코드로 데이터를 연결합니다.
- 지역 자료: 지역 코드·지역명·시군명·위도·경도. 좌표계는 WGS84로 통일하고 중심점은 대표 위치로 표시합니다.
- 지표 자료: 지역 코드·지표 이름·원자료 값·단위·출처 ID·자료 기준일·결측 여부.
- 점수 결과: 지역 코드·사용한 평가축·항목별 점수·종합점수·데이터 충족 여부·계산 버전.
- 팀장→팀원 2 함수: 지역별 지표와 사용자 가중치를 입력하면 항목 점수·총점·순위·추천 근거를 반환합니다. 입력 오류와 결측 처리 책임은 팀장이 맡습니다.
- 예외: 모든 가중치가 0인 입력은 계산하지 않고 안내합니다. 자료 없음은 0점으로 바꾸지 않습니다.

GitHub는 하나의 저장소를 사용합니다. 팀장은 `codex/backend`, 팀원 1은 `codex/planning`, 팀원 2는 `codex/frontend`, 팀원 3은 `codex/data` 브랜치를 사용하고, 공용 데이터 형식 변경은 팀에 먼저 알립니다. 팀장이 기술적 통합을 확인하고 팀원 1이 사용자 흐름을 확인한 뒤 시연 가능한 `main` 상태를 기록합니다. 00:30과 10:00에는 실행 확인한 커밋을 기록해 복구 기준으로 삼습니다. API 키·가상환경·개인정보는 저장소에 넣지 않습니다.

## 시간이 부족할 때의 결정 규칙

1. **16:00 데이터 수집 종료:** 한 도시와 공통 평가축을 고정합니다. 이후 새 도시·새 데이터 종류를 탐색하지 않습니다.
2. **6개 축 중 확보하지 못한 항목이 있으면:** 비교할 모든 지역에 동일한 축을 사용하고, 남은 기본 가중치의 합이 1이 되도록 재계산합니다. 화면에 사용·제외 항목을 표시하고 결과를 ‘확보된 항목 기반 시범 점수’로 명명합니다. 지역마다 서로 다른 축으로 만든 점수를 같은 순위에 섞지 않습니다.
3. **일부 지역만 자료가 부족하면:** 해당 지역은 부족한 항목을 표시하고 종합 순위에서 제외합니다. 실제 시설이 없다는 확인과 자료 미수집을 구분합니다.
4. **지도 경계 자료가 어렵다면:** 동네 대표 좌표의 점 지도와 비교표로 완성합니다. 직선거리를 도보 시간으로 표현하지 않습니다.
5. **AI 질의응답:** 필수 기능에서 제외합니다. 필요성이 있고 22:00 핵심 시연이 통과한 경우에만 한정된 기능으로 검토하며, 실패 시 규칙 기반 추천 설명으로 돌아갑니다. 이를 학습 모델의 추천이라고 표현하지 않습니다.
6. **온라인 배포:** 제출 규정상 필수가 아니라면 후순위입니다. 로컬 실행 가능한 제출본 확보를 우선합니다.
7. **10/31 00:30 기능 동결:** 이후에는 오류 수정·검증·발표만 합니다. 10:00에는 제출물도 고정합니다.

감축 순서는 **추가 도시·AI 챗봇 → 필수가 아닌 온라인 배포·실시간 API → 복잡한 지도 도형·시각 효과**입니다. 프로그램 실행, 실제 데이터의 근거, 점수 계산, 동네 비교, 발표자료는 끝까지 유지합니다.

실제 자료를 확보하지 못한 경우 가상 데이터로 계산 성능을 검증했다고 주장하지 않습니다. 테스트용 데이터는 개발에만 사용하고, 제출본이 시연용 가상 데이터에 의존하면 화면과 발표자료에 그 상태를 명시해야 합니다. 이는 실제 지역 평가를 완성한 것과 다른 결과이므로 16:00 회의에서 즉시 범위를 재조정합니다.

## 제출 전 통과 기준

- 다른 팀원 PC에서 README의 절차대로 프로그램을 실행할 수 있습니다.
- 제출 폴더에 코드·필수 데이터·의존성 목록·실행 안내가 모두 있습니다. 개발자 컴퓨터의 절대경로에 의존하지 않습니다.
- 지역 선택 → 점수 확인 → 두 동네 비교 → 가중치 변경 → 추천 갱신의 흐름이 작동합니다.
- 수작업 검산과 코드 계산이 일치하고, 같은 데이터·가중치에서 같은 결과가 나옵니다.
- 빈 결과, 결측, 가중치 합계 0, 후보 지역 5개 미만에서도 오류 없이 안내합니다.
- 각 지표의 기준일과 출처를 확인할 수 있고, 실제 데이터와 테스트 데이터가 구분되어 있습니다.
- 지도 네트워크에 문제가 있어도 점수·비교표와 핵심 시연은 유지됩니다.
- 발표자료의 수치·화면·기능 설명이 제출 프로그램과 일치합니다.
- 프로그램 ZIP을 다시 풀어서 실행하고, 발표 원본과 PDF의 글꼴·레이아웃을 확인합니다.
- 지정된 제출처에 프로그램과 발표자료를 업로드하고 접수 결과를 확인합니다.

## 발표자료 구성 제안
